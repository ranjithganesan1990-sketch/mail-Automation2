Mail Automation / Gmail connection guide

Connecting Gmail

Creating the Google OAuth client, and getting the redirect URI right the first time.

First: what the redirect URI actually is

This is the step that trips everyone up, so it is worth thirty seconds before you touch the console.

1 · YouClick Connect Gmail in the dashboard
→
2 · GoogleShows the consent screen and you approve
→
3 · Redirect URIGoogle sends the browser back here, carrying a one-time code
→
4 · AppTrades that code for tokens and saves the mailbox

So the redirect URI is an address inside your own app that already exists — not a page you have to build, and not a value you invent. Google refuses to send anyone to an address you have not registered in advance, which is the only reason you paste it into the console by hand.

Three rules cover every mistake people make with it:

  • It must match character for character. A trailing slash, http where it should say https, or a different port number is a completely different URI as far as Google is concerned.
  • One OAuth client can hold several. You do not need a second client for your deployed site — add both addresses to the client you already have.
  • It points at the API, not at the page you end up looking at. The API receives the code, then bounces you to the dashboard.

Your two exact values

Register both on the same OAuth client. Local and deployed then both work, and you never have to think about this again.

Local development
http://localhost:4000/api/mail-accounts/oauth/callback
Render deployment
https://mail-automation-c7i9.onrender.com/api/mail-accounts/oauth/callback
Leave GOOGLE_REDIRECT_URI unset on Render

The server builds this address itself from the URL Render assigns the service. Setting the variable by hand only creates a chance for the two to disagree — and a disagreement is precisely the failure you are trying to avoid.

Creating the credentials

01

Open a Google Cloud project

console.cloud.google.com → project picker → New Project

Any project works. Name it something you will still recognise in a year; mail-automation does the job. Reuse an existing project if you already have one.

02

Turn on the Gmail API

APIs & Services → Library → search “Gmail API” → Enable

Nothing else needs enabling. Skip it and the credentials still get created quite happily — then every send fails much later with a permission error, so do it now.

03

Fill in the consent screen

APIs & Services → OAuth consent screen
  • User type External, unless you pay for Google Workspace and will only ever connect company mailboxes.
  • App name and support email — these appear on the approval screen the mailbox owner sees.
  • Under Test users, add every Gmail address you intend to connect, including your own.
Skipping test users is the second most common failure

Mail Automation asks to read and send mail, which Google treats as sensitive. While the app is in Testing, only the addresses listed here can grant that. Everyone else gets “Access blocked” and no useful explanation.

04

Create the OAuth client

APIs & Services → Credentials → Create credentials → OAuth client ID
  • Application type: Web application. Not Desktop — a desktop client cannot use these redirect URIs at all.
  • Leave Authorised JavaScript origins empty. This app has no use for it.
  • Under Authorised redirect URIs, click Add URI twice and paste both values from the previous page.

Paste rather than retype. One wrong character produces an error message that looks nothing like a typo.

05

Keep the client ID and secret

Google shows both once, on a panel straight after you click Create. The ID always ends in .apps.googleusercontent.com. Losing the secret costs you nothing much — generate a fresh one on the same client rather than starting over.

The secret is a password

Anyone holding it can request Gmail access in your name. Keep it out of screenshots, commits and chat messages.

06

Give them to the app

Two routes that do the same job. The app reads its database first and falls back to environment variables, so whichever you choose, the other stays available.

  • Through the dashboard. Settings → Google OAuth → paste both → Save credentials. Restricted to the instance owner, which means a member of the oldest workspace on that server.
  • Through the environment. Set GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET. On Render that is the Environment tab, and saving restarts the service for you. Use this when the Settings card is not available to your account.

Credentials live in the database, not in the code, so configuring your local copy does nothing for the deployed one. Each site needs doing once.

07

Connect the mailbox

Mailboxes → Connect Gmail

Approve the request while signed in as the mailbox owner. The app stores an encrypted refresh token, so sending carries on without anyone signing in again, and the mailbox appears with a green status once it lands.

When it fails

The first two happen on Google’s side and never reach the app. The rest come back as a code in the dashboard’s address bar.

What you seeWhat it meansWhat to do
redirect_uri_mismatch The address the app sent matches none of the URIs registered on the client. Compare the two strings character by character. Usual culprits: a trailing slash, http against https, or the deployed URI never added.
Access blocked That Google account is not a test user, on an app still in Testing. Add the address under OAuth consent screen → Test users.
exchange_failed Google rejected the code-for-token swap. The client secret is wrong, truncated, or belongs to a different client than the ID.
expired_state Too long passed between starting the flow and approving it. Click Connect Gmail again.
access_denied The permission request was declined on the consent screen. Retry and accept. If there is no accept button to press, you are hitting the test-user problem above.
missing_code Google came back without an authorisation code. Almost always a stale or hand-edited callback URL. Start again from the dashboard.
no_email The profile permissions were not granted. Reconnect, leaving every requested permission ticked.
plan_limit The workspace already holds as many mailboxes as its plan allows. Remove a mailbox, or move up a plan.

Two things that bite later

Testing mode expires refresh tokens after seven days

While the consent screen stays in Testing, Google invalidates stored refresh tokens on a weekly cycle, and every connected mailbox quietly stops sending until somebody reconnects it. Fine while you are trying the app out. Publish the consent screen before you depend on it.

Never rotate ENCRYPTION_KEY once a mailbox is connected

That key decrypts the stored refresh tokens. Change it and every existing mailbox becomes unreadable with no way back — each one has to be connected again from scratch.
